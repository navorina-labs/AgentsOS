# 01. Анализ проблемы

## 1. Контекст

К 2025–2026 году индустрия находится в разрыве между **готовыми стандартами** и **неготовой инфраструктурой**:

- NIST финализировал ML-KEM (FIPS 203), ML-DSA (FIPS 204) и SLH-DSA (FIPS 205); FN-DSA выбран для будущего FIPS 206.
- Миграция в организациях идёт медленно: legacy, совместимость, неясный инвентарь «где именно RSA».
- Активна угроза **Harvest Now, Decrypt Later (HNDL)**: ciphertext перехватывают сегодня, расшифровывают после появления CRQC.

Проект **SafetyOS** не заменяет liboqs/OpenSSL, а отвечает на вопрос: **какие потоки данных критичны сейчас** и **что менять в каком порядке**.

## 2. Формальная модель противника

### 2.1 Классы возможностей

| Класс | Обозначение | Что ломает |
|-------|-------------|------------|
| Классический полиномиальный | P | Слабые протоколы, малые ключи |
| Квантовый (BQP) | BQP | RSA, DH, ECDH, ECDSA (Шор); ускорение перебора симметрии (Гровер) |
| ИИ-усиленный классический | P + heuristics | Реализация, side-channel, misconfig, утечки секретов |

**Важно:** LLM не переводит задачу факторизации RSA в полином на классическом железе. ИИ усиливает **слой B** — инженерию и операции.

### 2.2 Определение «взлома»

Безопасность — игра: противник \(A\) с бюджетом \((T, M)\) должен с неничтожной вероятностью \(\varepsilon\) восстановить секрет \(k\) или сообщение \(m\) из допустимого набора наблюдений (ciphertext, подписи, оракулы).

SafetyOS оперирует не доказательствами стойкости алгоритма, а **операционным риском**: вероятность компрометации потока при заданном профиле противника и горизонте времени.

## 3. Теорема Моски и HNDL

\[
\text{риск сегодня} \iff x + y > z
\]

| Переменная | Смысл | Единицы |
|------------|-------|---------|
| \(x\) | Срок конфиденциальности данных | годы |
| \(y\) | Время миграции организации на PQC | годы |
| \(z\) | Горизонт появления CRQC (оценка) | годы |

Дополнительно: флаг **HNDL exposure** — ciphertext уже мог быть перехвачен. Тогда даже успешная миграция завтра не спасает старые записи без **re-encryption** и ротации ключей.

---

## 4. Что предлагает рынок и где пробел

| Подход | Ограничение |
|--------|-------------|
| «Внедрите ML-KEM» | Нет привязки к сроку жизни данных и инвентарю |
| Гибрид TLS | Не закрывает архивы и at-rest |
| Zero Trust | Не заменяет математику ключей |
| QKD | Масштаб и доверие к оборудованию |
| SIEM + ИИ | Без криптографической модели потоков |

**Пробел SafetyOS:** количественная приоритизация по потокам + непрерывный CBOM + политики CI на основе Mosca score.

## 5. Две ортогональные оси защиты

```
                    Квант (математика)
                           │
         PQC KEM/DSA ──────┼────── Hybrid TLS
         AES-256 at-rest ─┼────── Forward secrecy
                           │
    ───────────────────────┼──────────────────────► Время (HNDL, retention)
                           │
         ИИ/автоматизация ─┼────── Fuzz, static analysis
         (реализация)      ┼────── Secret scanning
                           │
```

## 6. Рекомендуемый стек алгоритмов (2026)

| Назначение | Рекомендация |
|------------|--------------|
| Key exchange | ML-KEM-768 (enterprise), ML-KEM-1024 (высокий профиль); гибрид с X25519 на переходе |
| Подписи | ML-DSA; SLH-DSA для root/долгого архива |
| Симметрия | AES-256-GCM или ChaCha20-Poly1305 |
| Хеш | SHA-256 / SHA-384 |
| Устаревшее | RSA &lt; 3072, ECDSA с малыми кривыми, SHA-1, MD5 — маркировать как critical |

---

## 7. Размышления для продукта

1. **Crypto agility** важнее выбора одного «вечного» PQC-алгоритма.
2. **Инвентарь** важнее скорости внедрения первого KEM.
3. **Re-encryption** обязателен при HNDL + долгом \(x\).
4. **ИИ в SafetyOS** — только defensive assurance, без обещаний «взлома AES».
